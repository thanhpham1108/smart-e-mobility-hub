# Smart Charging — Method descriptions

**Owner:** Phạm Nguyễn Công Thành — 2453175. **Use cases:** UC-C01–C03; interfaces with UC-P02/P05, UC-I03/T03 and What-if. [Class diagram](../class-diagram/smart-charging/05-smart-charging.puml) · [Inventory](../class-diagram/smart-charging/05-smart-charging-inventory.md).

## Data contracts and shared rules

- `ChargingDraft` carries parking reference when applicable, Hub, vehicle, current/target battery percentages and requested start/end. Parking has already checked its own reservation, owner and parking window. Charging rechecks eligibility before allocating. An internal fleet request may have no parking reference.
- `ChargingOverview` returns Scheduled and Waiting requests in FCFS order, waitlist positions, their allocations when assigned, current schedule and point states. `ChargingSnapshot` is an immutable, versioned copy of charging state for the shared `NetworkSnapshot` contract.
- `ChargingSessionEvent` is a verified telemetry/control contract with event ID, kind (START, STOP, SUSPEND, RESUME or TARGET_REACHED), request/session/point/vehicle IDs and actual event time. A STOP following a Student action carries the confirmed `ChargingStopChoice`. It is a data contract, not another owned entity in this three-use-case diagram.
- `ChargingStopChoice` is the Student's explicit `COMPLETE` or `CANCEL` action for an active session. It determines the terminal request status; a target-reached event always completes the request.
- Order requests per Hub by `submittedAt`, then lower `currentBatteryPercent` only at identical timestamps, then `requestId`. A valid future-start request is `Waiting` without an allocation until `requestedStart`; do not show `Full` solely because its start is in the future. A currently eligible request blocked by full capacity is also `Waiting` without an allocation; show `Full` and its live queue position. Promote eligible waitlisted requests automatically when their start arrives and a point is free, or when a point actually becomes free. Estimated duration never rejects a valid request. Expire waiting requests when their requested window ends and notify the Student. Cancel a Scheduled request if no verified START arrives within 15 minutes of its allocation start; release its point and promote the next eligible waiting request.
- All writes recheck current state and commit as one unit with dependent status/allocation changes. Every committed allocation add/move/release increments `ChargingSchedule.version`; point eligibility is rechecked in the same transaction. The service also checks the vehicle's commitments at other Hubs before creating an overlapping allocation. Failure leaves the last valid schedule and committed requests unchanged. A duplicate request key with the same draft returns its original result; reuse with different data is rejected.
- A draft that already meets its target is rejected as `NoChargingRequired` before a request is saved. Accepted requests begin in `Scheduled` or `Waiting`, according to capacity. When verified battery telemetry reaches `targetBatteryPercent`, transition `Charging` → `Completed` and release the charging point immediately. A confirmed Student **Complete** action also ends the session as `Completed`; **Cancel** ends it as `Cancelled`. A `Waiting` request has no allocation; `Scheduled` and `Charging` requests hold one until completion or cancellation.
- Keep `ChargingRequest.requestedEnd` and `ChargingAllocation.endTime` as the Student's requested and assigned **planned** end times. They support display and Waiting expiry; neither is an actual stop event. A `Charging` or `Suspended` request continues to occupy its point beyond either end time until a verified completion/cancellation. Do not promise a future point based solely on a planned end time.

| `ChargingService.getQueueAndSchedule(hubId: String): ChargingOverview` | UC-C01: show one Hub's Scheduled and Waiting requests and schedule. | Hub ID → FCFS ordered scheduled and waiting requests, queue positions, allocations, current schedule and point status. | Authorized Operator; Hub and required state readable. | Read-only; order uses submission timestamp and exact-timestamp tie rule. | Missing request/schedule/point data: report unavailable; never present a partial snapshot as current. |
| `ChargingService.generateSchedule(hubId: String): ChargingSchedule` | UC-C02: update the Hub schedule on submission, requested-start arrival, capacity release or periodic timeout scan. | Hub ID → saved current schedule; `submitRequest` separately returns the request and its queue position when Waiting. | Current point state and active allocations available; use server time for start eligibility, expiry and timeout. | Assign only a point that is currently free when `requestedStart ≤ now < requestedEnd`, with no earlier eligible Waiting request. A future-start request stays Waiting without a guaranteed point. A planned end time does not free a point. If current capacity is full, leave the eligible request Waiting without changing allocations. | `ChargingService.adjustAllocation(allocationId: String, pointId: String, startTime: DateTime, endTime: DateTime, expectedVersion: int): ChargingAllocation` | UC-C03: modify an existing assignment's point or planned interval. | Allocation ID, proposed point/planned interval and version the Operator reviewed → updated allocation. | Operator; current schedule loaded at `expectedVersion`; point operational and currently free for a reassignment; valid proposed interval within request/parking window with `startTime ≤ now < endTime`; allocation is Scheduled, not Charging/Suspended. | Recheck point and vehicle commitments, current occupancy and version; reject a move that bypasses an earlier eligible request under FCFS; atomically replace only the selected allocation, then return current result. The planned end remains display-only; adjustment cannot hold a future point. | Faulty/unavailable or occupied point, future start, FCFS violation, stale version or save failure: reject and retain existing allocation/schedule. |
| `ChargingService.submitRequest(draft: ChargingDraft, key: String): ChargingRequest` | Accept and schedule a request from Parking or an authorized internal flow. | Draft and retry key → Scheduled request with allocation, or Waiting request with queue position. | Valid source/owner, Hub/vehicle/window, `0 ≤ current < target ≤ 100`, eligible parking where relevant. | Calculate an informational estimate when configuration is available, then apply the FCFS rule. Persist Scheduled plus allocation only when the requested start has arrived and a point is currently free; otherwise save Waiting without allocation. A future-start Waiting response is not labeled Full; equivalent retry returns the same result. | Invalid draft, unavailable authoritative point data or failed save: show reason and create no request. Full current capacity creates a Waiting entry; an unavailable estimate alone does not reject the request. |
| `ChargingService.cancelRequest(requestId: String): ChargingRequest` | Cancel a request before charging starts. | Request ID → Cancelled request. | Authorized owner/caller; request is Waiting or Scheduled. | Mark Cancelled; remove from the waitlist or release its held Scheduled allocation once; parking booking remains unchanged if only charging is cancelled. | Unknown/terminal/Charging request or failed write: preserve current commitments. Identical retry returns existing cancellation. |
| `ChargingService.stopCharging(requestId: String, choice: ChargingStopChoice, confirmedAt: DateTime): ChargingRequest` | Stop an active session when the Student chooses **Complete** or **Cancel**. | Request ID, explicit choice and verified stop time → terminal request. | Trusted stop confirmation matches the Charging/Suspended request, session, point and vehicle. | `COMPLETE` marks the request Completed; `CANCEL` marks it Cancelled. Either confirmed action releases the point immediately and preserves actual battery level and stop time in history. A verified target-reached event always marks Completed. | Unverified/mismatched stop, stale time or failed commit: keep charging state and point commitment; return reconciliation error. |
| `ChargingService.reconcileSessionEvent(event: ChargingSessionEvent): ChargingRequest` | Apply one verified start, stop, suspend, resume or target-reached event from Fleet/telemetry. | Event with unique ID, kind and request/session/point/vehicle/time → updated request. | Trusted source; current allocation and parking eligibility match a START; event is fresh and not already applied. START requires Scheduled and no other active session for the vehicle/point; STOP requires matching Charging/Suspended session and its confirmed Student choice; TARGET_REACHED requires Charging and observed battery at or above target. | Persist actual session reference/time once. TARGET_REACHED marks Completed and releases the point. A confirmed STOP applies the Student choice: COMPLETE → Completed, CANCEL → Cancelled; either releases the point once. An idle point observation alone does not stop a session. | Unmatched, stale or contradictory event: return reconciliation required, keep commitments and set `reconciliationHold` on the point; only a later verified reconciliation clears that hold. Duplicate event returns its prior result. |
| `ChargingService.recordPointObservation(pointId: String, status: PointStatus, observedAt: DateTime): ChargingPoint` | Apply accepted physical point condition from Fleet/telemetry. | Identified, validated condition and observation time → point state. | Trusted source has validated identity, freshness and duplicates; point exists. | Update condition/freshness; a fault prevents **new** allocations and flags affected ones for review. A healthy observation alone does not clear incident restrictions. Existing held allocations are not silently deleted. | Stale/invalid observation: reject/no new availability. Idle observation never cancels a held Scheduled allocation. |
| `ChargingService.setPointRestriction(pointId: String, incidentId: String, active: boolean): ChargingPoint` | Add or remove exactly one incident restriction. | Point ID, incident ticket ID and add/remove flag → point with updated restrictions. | Trusted IncidentService caller; the incident references this point. Removal requires verified resolution of that ticket under the shared transaction. | Add/remove only `incidentId`; a different unresolved fault remains active. Recompute eligibility from physical condition, remaining restrictions and commitments. | Unknown/mismatched incident, premature removal or failed commit: retain restrictions and point eligibility. Repeated identical command is safe. |
| `ChargingService.getChargingSnapshot(): ChargingSnapshot` | Supply What-if and shared snapshot assembly with charging data. | No input → versioned, immutable charging view. | Snapshot contract can read a consistent module state. | No live state change; includes points, requests, allocations, schedule version and data freshness. | Inconsistent/unavailable data: fail snapshot rather than substitute zeros or a mixed version. |
| `ChargingPoint.isOperational(): boolean` | Check whether a point can accept new allocations. | No input → boolean. | Point has verified status. | Read-only; true only when status is Operational, `activeRestrictionIds` is empty and `reconciliationHold` is false. | Unknown/stale condition is not treated as operational. |
| `ChargingAllocation.overlaps(other: ChargingAllocation): boolean` | Detect overlap between two **planned** intervals. | Other allocation → boolean. | Both planned intervals valid; caller has checked same point or compares point IDs. | Read-only; true iff same point and `start < other.end` and `other.start < end`; touching endpoints do not overlap as planned intervals. This calculation does not free a point held by an active session. | Missing/invalid interval: validation failure; do not claim no conflict. |
| `ChargingSchedule.hasConflict(pointId: String, vehicleId: String, startTime: DateTime, endTime: DateTime, excludeAllocationId: String): boolean` | Check a proposed point/vehicle/planned interval against current commitments. | Point, vehicle, planned interval and current allocation ID to ignore → boolean. | Valid interval; schedule current for Hub; point belongs to Hub; vehicle identity known. | Read-only; report conflict for a point or vehicle held by `Scheduled`, `Charging` or `Suspended` regardless of its planned end. `overlaps` may compare historical/planned intervals for display, but `hasConflict` never infers actual release from `endTime`. | Invalid/stale plan or data: reject validation; a false result requires a complete current plan and current request statuses. |

**Cross-module handoff:** Parking owns parking eligibility; Charging returns either a Scheduled request with allocation or a Waiting request with Hub queue position when capacity is full. Fleet owns incident evidence; What-if reads a copied snapshot. Parking cancellation, no-show expiry and checkout cancel linked Waiting or Scheduled requests before charging begins; Waiting requests are removed from the queue.
