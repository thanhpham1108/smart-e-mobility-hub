# Fleet & Incident - Class and Method Design

Owner: Mai Hoang Phuong Dong - 2452265 (member 4).

Class diagram: [04-fleet-incident.puml](../class-diagram/fleet-incident/04-fleet-incident.puml).

Scope: UC-F01-F05, UC-I01-I03, UC-T01-T03 and UC-S03; background support for FR-NI-01/02/03/05/06/07/08. UC-I01 is abstract. IncidentService handles its vehicle and charging-point specializations using a typed resource reference. Rental, parking and charging policies remain owned by their respective modules.

## 1. Design decisions and class responsibilities

- FleetService coordinates read-only monitoring and redistribution transactions. It is also the internal entry point for periodic freshness and imbalance evaluation.
- IncidentService is an added member-4 service separating investigation, repair and restoration from fleet movement. This refines the initial FleetService proposal without adding a new team module.
- TelemetryAdapter authenticates event sources, validates/deduplicates observations and routes accepted updates through Rental, Parking or Charging contracts.
- RedistributionOrder owns assignment progress and risk state. IncidentTicket owns fault evidence, response references and its lifecycle. Neither entity directly changes another module's resource.
- API controllers from Submission 2 remain thin boundary handlers. FleetDashboardController and RedistributionController delegate to FleetService; IncidentController delegates to IncidentService; TelemetryController delegates to TelemetryAdapter. The former FeasibilityService responsibility is included in FleetService.validateRedistribution. This is a design refinement, with the same UC-S03 checks.
- The initial in-browser mockup is a UI prototype. This design places authoritative decisions in one application process as agreed in the architecture baseline.

## 2. Common contracts

### Authorization, atomicity and retries

All public Context-based queries require a valid Operator session, except reportFailure, which additionally accepts a server-authenticated Student report for their own relevant rental or a trusted internal telemetry identity. Public callers cannot grant themselves an internal identity. evaluateNetworkHealth is an internal scheduled/domain-event operation. Entity methods are not public API endpoints.

Every mutation uses a requestId scoped to its authenticated principal and operation, plus a canonical payload hash. Same key and same payload returns the original committed result. Reusing a key with different content produces RequestConflict. Writes to existing orders/tickets require expectedVersion; check idempotency before checking that version so a committed retry still succeeds. Empty or malformed IDs, missing fields and invalid enums fail validation before mutation.

The MVP uses a single shared in-memory Unit of Work. A mutation acquires the application state lock, reads/revalidates owner state, stages all changes on a working copy and publishes the copy with its result record and audit entry only if every check succeeds. Exceptions discard the staged copy. Rental, Hub, Parking and Charging contracts participate in this same unit; no network transaction across independent services is assumed. A lost acknowledgement is resolved by retrying the original key. In-memory results are retained for the application lifetime; restart/durable recovery is outside this MVP and requires persistent storage if added later.

An assignment commits the selected vehicles to the transfer but does not reserve destination capacity or record physical movement. Arrival confirmation rechecks destination capacity and changes confirmed Hub/location and occupancy exactly once. Telemetry stores observed location separately: it cannot confirm UC-F05 implicitly. Hub counters are projections of owner state and are refreshed in the same commit, rather than being independent competing sources of truth.

### States and invariants

OrderStatus: Assigned, InTransit, PartiallyCompleted, AtRisk, Completed, Cancelled. IncidentStatus: Reported, Investigating, ActionAssigned, InRepair, Resolved, Closed. ResourceType: VEHICLE or CHARGING_POINT. Severity: LOW, MEDIUM or HIGH. These retain the Submission 2 names; the same incident guards are applied to charging-point incidents as a Submission 3 generalization.

- Order creation starts at Assigned. DISPATCH permits Assigned to InTransit. Newly verified arrivals calculate PartiallyCompleted or Completed from the arrived set. AtRisk preserves resumeStatus; successful revalidation restores Assigned, InTransit or PartiallyCompleted as appropriate. Cancellation is allowed before departure from Assigned, or from AtRisk after all unarrived vehicles have verified disposition and remaining vehicle commitments can be released safely. Completed/Cancelled are terminal. A physically unlocated/in-transit vehicle must be reconciled before cancellation releases its commitment.
- Incidents progress Reported to Investigating to ActionAssigned to InRepair, with progress self-updates. Verified recovery permits ActionAssigned/InRepair to Resolved. Only Resolved can close. A new matching fault before closure reopens Resolved to Investigating and invalidates repair clearance; a fault after Closed creates a new ticket.
- Only IncidentService.resolveIncident can coordinate restoration. Repair evidence, current condition, all other unresolved faults and affected owner commitments are checked under the same state lock. Removing this incident's restriction is not equivalent to setting a reserved/rented/assigned vehicle Available. The owner derives its eligible state from all remaining commitments.
- Equivalent incident means the same resourceType + resourceId + faultKey. Distinct faults may coexist; resolving one must not remove another's restriction. A student report and telemetry evidence for the same fault are linked when their normalized faultKey matches.
- Staleness and imbalance thresholds are configuration, not UI constants. At now - observedAt >= staleInterval an observation is stale (boundary convention chosen for this design). Imbalance evaluation ignores unavailable/stale capacity for actionable recommendations and instead raises a data-quality alert.

## 7. Cross-module agreements and traceability

Fleet queries Hub status, Rental vehicles/commitments, Parking capacity/reconciliation and Charging point/session/schedule status. The same owners apply Fleet-authorized restrictions, movement updates and restoration through explicit in-process contracts. These contracts are proposed integration agreements for owner review, not redefinitions of their classes.
