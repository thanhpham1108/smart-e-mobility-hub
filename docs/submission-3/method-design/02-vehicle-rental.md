# Vehicle Rental — Method descriptions

**Use cases:** UC-R01–UC-R08; UC-X01; UC-S01 (included availability check). Related non-interactive requirements: FR-NI-01, FR-NI-02, FR-NI-04, FR-NI-05.

| `SharedVehicle.isAvailable(): boolean` | Determine whether a vehicle is eligible for a new allocation. | No input; returns `boolean`. | Vehicle has a valid lifecycle status and operational condition. | No state change. | `SharedVehicle.isOperational(): boolean` | Check whether the vehicle is in working condition. | No input; returns `boolean`. | Vehicle condition is known. | No state change. | `SharedVehicle.reserve(): void` | Transition an eligible vehicle to reserved state. | No input; returns `void`. | Vehicle is available and operational; service has atomically checked allocation conflicts. | Status becomes `RESERVED`; allocation is committed together with the reservation record by the service. | Ineligible state or conflict: reject transition; no new allocation. |
| `SharedVehicle.releaseReservation(): void` | Release a vehicle after cancellation or expiry of its reservation. | No input; returns `void`. | Service has verified that the allocation belongs to the cancelled/expired reservation and no active trip or newer allocation exists. | `RESERVED` becomes `AVAILABLE` if operational, or `UNDER_MAINTENANCE` if faulted. | `VehicleReservation.isEligibleForCancellation(now: DateTime): boolean` | Determine whether a reservation may be cancelled by its owner. | `now`: authoritative current time; returns `boolean`. | Reservation exists with valid timestamps and status. | No state change. | `VehicleReservation.markPickedUp(): void` | Consume the reservation after successful vehicle pickup. | No input; returns `void`. | Reservation is confirmed and eligible at the service's authoritative pickup check; matching vehicle is unlocked and no trip has already been created. | Status becomes `PICKED_UP`; reservation cannot be cancelled or expired. | `VehicleReservation.cancel(): void` | Mark an eligible reservation as cancelled. | No input; returns `void`. | Service has verified ownership, cancellation eligibility and no active rental. | Status becomes `CANCELLED`; allocation release is coordinated atomically by the service. | Picked-up, expired or otherwise ineligible reservation: reject. | `VehicleReservation.expire(): void` | Record automatic expiry of an unused reservation. | No input; returns `void`. | Reservation is `CONFIRMED`; service has verified the deadline has passed and rental has not started. | Status becomes `EXPIRED`; service releases the matching allocation according to current vehicle state. | Deadline not reached or rental started: reject transition. Already expired: no additional mutation. |
| `RentalTrip.isActive(): boolean` | Check whether the trip is still in progress. | No input; returns `boolean`. | Trip has a valid status. | No state change. Returns `true` only for `ACTIVE`. | Missing or invalid status: return `false`. |

## Design notes and cross-module contracts

- **State ownership and storage:** Vehicle Rental owns `SharedVehicle`, `VehicleReservation` and `RentalTrip`. The application/API layer checks session and Student role; trusted internal calls handle telemetry and expiry. JSON fixtures seed authoritative in-memory state. References to the Rental Database in Submission 2 represent logical storage, not a separate required database. Cross-module changes must be coordinated atomically at the application level.
- **Time and reservation boundary:** Use authoritative timestamps (ISO 8601, GMT+7 for user-facing intervals). A reservation is eligible before `expiresAt`, not at the deadline. The agreed diagram distinguishes `EXPIRED` from `CANCELLED`; the timeout activity diagram describes automatic cancellation, which is represented here by `EXPIRED` for an elapsed deadline. Duration is elapsed whole minutes (proposed rounding convention).
- **Vehicle lifecycle:** Follow `SCD_VehicleLifeCycle.puml`. The return sequence uses `UNAVAILABLE` for a faulted vehicle; the agreed class diagram represents that outcome as `UNDER_MAINTENANCE`. `VehicleCondition` is separate from lifecycle status so an active trip can remain active after a fault. For a fault during reservation, the booking must not permit pickup; cancellation/expiry or an agreed incident-resolution policy resolves the hold. Restoration must not make an allocated vehicle available to another Student. Exact fault/redistribution coordination is to be agreed with Fleet.
- **External contracts:** Use HubService for Hub status/search/alternatives, ParkingService for pickup/return parking coordination, and FleetService for incident submission and operational restrictions. The exact ParkingService/FleetService operation signatures are not yet specified by their owners; this document does not define them. The return-space ID identifies a ParkingSpace owned by Member 3. IncidentTicket is owned by Member 4. Simulation reads a snapshot and does not mutate live rental state.
- **Device operations:** Unlock/lock and safe relock are required by the pickup/return sequence diagrams. The concrete device/simulator adapter is not defined in the agreed class diagram; the service descriptions retain the required behavior without introducing new operations. A physical operation cannot be rolled back by a logical transaction alone; failed commits require recovery/reconciliation.
- **Idempotency and errors:** The architecture baseline requires duplicate submissions to return the original result. The agreed signatures do not contain a request ID; request correlation/deduplication must be supplied by the shared application layer (exact mechanism pending). Do not treat a new legitimate rental as a retry based only on Student and vehicle IDs. Errors in the table are semantic outcomes mapped by the application layer; no new result types or exception classes are introduced.
- **Data details pending agreement:** The agreed diagram uses `currentHubId: String` and a `0..1` Hub association; this document interprets the reference as absent while travelling. `hubId` in telemetry represents a reported Hub when known; absence/in-transit representation must be aligned with the shared telemetry contract. Trip distance is supplied by validated measured/simulated data; the source and fallback are not fixed in Submission 3. Do not invent a distance on missing data. The team must settle these details before implementation.
