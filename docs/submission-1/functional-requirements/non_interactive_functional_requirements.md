# Other Non-Interactive Functional Requirements

## 1. Purpose and Scope

This document specifies functional behaviour that is initiated automatically by an incoming event, a timer, or a domain-state change rather than by a Student or Operator directly selecting a system function. These requirements complement the interactive use cases; they do not replace them.

All configurable thresholds mentioned below, such as a low-battery threshold, telemetry-staleness interval, reservation-expiry interval, or Hub imbalance threshold, must be defined by the project team and stored as configuration data rather than embedded in UI components.

## 2. Non-Interactive Functional Requirements

| **ID** | **Trigger** | **The system shall** | **Observable result / acceptance condition** | **Related Use Cases** |
|---|---|---|---|---|
| **FR-NI-01**<br>Validate and Apply Vehicle Telemetry | An External Telemetry Provider or mock-IoT timer sends identified vehicle telemetry. | Validate the vehicle identifier, timestamp, and required telemetry fields before applying the update. For an accepted update, it shall update the vehicle's latest location/Hub, battery level, and reported operational state, and record the data-freshness time. It shall reject an invalid or stale update without replacing a newer accepted state. | A valid event updates the matching vehicle and its freshness time. An invalid/stale event does not overwrite current data. | UC-F01, UC-F02, UC-I02 |
| **FR-NI-02**<br>Automatically Create or Update a Vehicle-Failure Incident | An accepted telemetry update reports a fault or an operational state that makes a vehicle ineligible for use. | Create a vehicle-failure incident when no equivalent open incident exists for the vehicle, or append the new evidence to the existing open incident. It shall restrict the vehicle from new allocations. | One open incident is available for Operator review; duplicate telemetry events do not create duplicate open incidents; the affected vehicle is not offered for new reservations or redistribution. | UC-I02, UC-R03, UC-F04 |
| **FR-NI-03**<br>Detect Stale Operational Data | The latest accepted status for a vehicle, Hub, parking resource, or charging point becomes older than the configured staleness interval. | Mark the corresponding status as stale and expose its latest accepted timestamp in operational views. It shall not present stale information as current. | Dashboard and detail views distinguish stale information from current information. | UC-F01, UC-F02, UC-F03 |
| **FR-NI-04**<br>Expire Unused Vehicle Reservations | A vehicle reservation reaches its configured expiry time and has not become an active rental. | Change the reservation to expired and release its vehicle allocation, provided that no other valid commitment or incident prevents the vehicle from becoming available. | The expired reservation is no longer eligible for pickup; the vehicle may become available only when its current operational condition permits it. | UC-R03, UC-R04, UC-R06, UC-R07 |
| **FR-NI-05**<br>Synchronize Resource States After a Domain Event | A confirmed reservation, cancellation, pickup, return, incident restriction, redistribution completion, parking check-in/check-out, or charging-state event changes resource availability. | Recalculate the affected vehicle, parking-space, charging-point, Hub-occupancy, and assignment states from the confirmed event. It shall prevent a resource from simultaneously appearing available and committed to incompatible work. | The affected views display one consistent state after the event; resource counts and individual resource states agree. | UC-R03–UC-R07, UC-P01–UC-P07, UC-F05, UC-I02 |
| **FR-NI-06**<br>Detect Hub Resource Imbalance | A confirmed vehicle or Hub state change occurs, or the configured periodic imbalance check runs. | Compare vehicle availability and resource utilization at each Hub against configured operating thresholds. When a Hub has a shortage, surplus, or capacity risk, it shall create an operational alert or redistribution recommendation. It shall not create a redistribution assignment or move vehicles automatically. | The Operator Dashboard displays the affected Hub and the reason for the alert/recommendation; no live vehicle movement occurs without Operator confirmation. | UC-F01, UC-F04, UC-W04 |
| **FR-NI-07**<br>Invalidate an At-Risk Redistribution Assignment | A vehicle in an incomplete redistribution assignment becomes unavailable, faulted, reserved, rented, or committed to conflicting work. | Revalidate the affected assignment, mark the affected vehicle or assignment as at risk, and create an operational alert. It shall not record redistribution completion for vehicles whose physical arrival has not been confirmed. | The Operator can see the assignment conflict and its reason; no unconfirmed vehicle location or occupancy update is made. | UC-F04, UC-F05, UC-I02 |
| **FR-NI-08**<br>Reconcile Parking Occupancy Observations | An accepted parking-occupancy observation is received from a sensor or mock-data event. | Reconcile observed occupancy with active parking sessions and reservations for the affected Hub. It shall update actual occupancy once for each occupied space and identify a discrepancy when observations do not match expected occupancy. | Hub occupancy is not double-counted; an occupancy discrepancy is visible to the Operator. | UC-H03, UC-P06, UC-P07, UC-F01 |
| **FR-NI-09**<br>Pause Charging When a Hub Becomes Offline | A Hub Offline event is applied in a What-if Simulation. | Change every active charging session at that Hub to `Paused` for the simulated state and stop charging-time progression for those sessions. It shall keep all simulated changes separate from live operations. | A simulated offline Hub has no active charging session that continues accumulating charging time; live charging data remains unchanged. | UC-W02, UC-W03 |
| **FR-NI-10**<br>Guard Scheduled Charging Start | A scheduled charging interval begins, or an assigned charging point changes state before the interval begins. | Check that the Hub is operational, the charging point is operational and available, and the allocation is still valid before starting the session. If validation fails, it shall not start the session and shall mark the allocation as affected or unscheduled with a reason. | A session never starts on an unavailable point or offline Hub; the affected allocation has a visible reason. | UC-C01, UC-C02, UC-C03 |
| **FR-NI-11**<br>Advance the Charging Queue After Capacity Is Released | A charging session completes, is paused, is cancelled, or a charging point becomes available. | Re-evaluate eligible pending charging requests using the configured rule-based priority policy and available capacity. It shall allocate the next feasible request without creating overlapping allocations and shall identify requests that remain unscheduled. | The next feasible queued request receives a non-conflicting allocation; unavailable requests remain unscheduled with a reason. | UC-C01, UC-C02, UC-S04, UC-S05 |
| **FR-NI-12**<br>Keep Simulation State Isolated From Live Operations | A What-if Simulation starts, evaluates an event, or finishes. | Obtain a consistent timestamped network snapshot, apply simulated changes only to the simulation state, and retain the live network state without modification. | Simulation results identify their baseline/snapshot; no live vehicle, reservation, occupancy, charging, or incident state changes as a consequence of the simulation. | UC-W02, UC-W03, UC-W05 |

## 3. Verification Notes

| **Requirement group** | **Representative verification** |
|---|---|
| Telemetry and freshness | Send a valid telemetry update, then an older update for the same vehicle. Verify that the valid update is shown and the older one is rejected. |
| Incident safety | Send repeated fault telemetry for one vehicle. Verify that one open incident is retained and the vehicle cannot receive a new reservation. |
| Reservation and resource consistency | Let a reservation expire without pickup. Verify that the reservation becomes expired and that the vehicle state is consistent with its other commitments. |
| Fleet redistribution | Make an assigned vehicle faulted before arrival. Verify that the assignment is flagged and the system does not record a completed movement. |
| Charging | Make a charging point unavailable at a scheduled start time. Verify that the session does not start and that the allocation is marked with its reason. |
| Simulation isolation | Simulate a Hub Offline event. Verify that simulated charging sessions are paused while the corresponding live state is unchanged. |

## 4. Traceability

- `FR-NI-01` to `FR-NI-03` support accurate, near-real-time fleet monitoring and incident handling.
- `FR-NI-04` and `FR-NI-05` preserve reservation and resource-state consistency.
- `FR-NI-06` and `FR-NI-07` support Operator redistribution decisions without automating physical movement.
- `FR-NI-08` to `FR-NI-11` support parking and charging resource coordination.
- `FR-NI-12` ensures that What-if Simulation remains an analysis tool rather than a live-operation command.
